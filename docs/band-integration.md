# Optional project Band agents

The portal implements a custom Band REST/WebSocket integration for four separately authenticated project agents. It is off by default. The main workspace keeps the user-selected dummy configuration; no live Band registration, room activity or bonus success is claimed. Tests intercept HTTP and sockets rather than post to Band.

## Setup and access review

1. In the project’s Band account, register four dedicated agent identities: Planner, Builder, Reviewer and Security. Save each agent UUID and its own `band_a_` API key in the corresponding `PROJECT_BAND_<ROLE>_AGENT_ID` / `_API_KEY` variables. All four IDs and keys must be distinct. The portal runs these agents; do not simultaneously run them through another Desktop/runtime process.
2. Create a dedicated room for each intended business and add exactly those four project agents. Additional listed human participants are allowed, up to 30 participants total. Verify ownership, organization settings and sharing in Band: agent owners or administrators may have access without appearing as room participants. The roster check is not a complete access audit.
3. Set `PROJECT_BAND_ENABLED=true`, the business’s `PROJECT_BAND_ALLCO_ENABLED=true` (or `HUASHENG`) and its existing `PROJECT_BAND_<BUSINESS>_ROOM_ID`. Enabled businesses must have different room UUIDs. The same four agent connections can join both reviewed rooms; their work remains scoped by business/room/run. No room, agent, contact or participant is automatically created or invited.
4. In **HITL review → Project Band team**, acknowledge and run **Check team & room**. It reads every configured agent’s identity and participant view using its own key. IDs, active membership and consistent rosters must match. Inspect all identities, listed participants and Band access settings, then explicitly connect the project agents.
5. Choose **Band team · source template** or **Band team · AI model** in the composer. Inspect and acknowledge the exact public packet. A model request also needs the existing explicit OpenAI processing acknowledgement and two-credit budget. Agent connection alone does not create a draft or send a room message.
6. Follow the agent activity and confirmed message IDs. Open **Review exact draft** when ready. A human must still inspect the recipient, copy and sources, approve that exact version, and separately choose dry run or configured live email.

Generic `BAND_API_KEY`, `band_u_` owner keys, Band Desktop sign-in files and global credentials are never read as fallback. Custom API/WS destinations are not accepted. Credentials stay in server closures; state, browser responses and messages contain no keys. `ws` is pinned at 8.22.0 for authenticated WebSocket headers. Do not place keys in URLs or commit `.env`.

## What the agents actually do

- **Planner:** creates a bounded plan from the owner-reviewed supplier/account request. This is a deterministic policy step. It posts a real mention to Builder and receives the final Security handoff.
- **Builder:** prepares/reuses the requested source-template variant, or invokes the explicitly authorized project OpenAI drafting path once. It uses the same profile/account/contact/credit gates, saved brief and model-output validation as direct drafting. A model result can create a draft only while its exact run/context remains eligible. No arbitrary Band text becomes a tool command.
- **Reviewer:** checks required account/supplier citation presence and objective message-brief constraints. It does not independently prove factual accuracy, buying authority, tone or consent.
- **Security:** checks HTTPS URL shape and membership in the draft’s allowed sources. It does not perform SAST/SCA, independent vulnerability scanning or a full data-loss audit.

These are self-hosted agent handlers, with optional model execution in Builder; they are not four independently reasoning models. Normal Band rooms/identities are visible through Band Desktop. The local discovery role summaries remain separate from this integration. No actor can approve a draft, change graph schema or dispatch email/LinkedIn. Graph queries and updates remain the existing graph-module workflow.

## Transport, state and recovery

REST uses only `https://app.band.ai/api/v1/agent` with `X-API-Key`. Each role has one WebSocket at the official `wss://app.band.ai/api/v1/socket/websocket` endpoint, header authentication, Phoenix V2 frames and `on_conflict=reject`. The client joins agent control/membership and explicitly reviewed room channels, sends heartbeats, performs bounded transient reconnects and catches up through `/messages/next`. Auth/conflict or supersede stops rather than displacing another runtime. No key is put in a query string.

Messages carry a versioned run envelope plus the exact reviewed public packet. Public supplier/account identifiers, application, selected product families, writing brief and fixed policy are shared. Contact addresses, private relationship/preference notes and commercial constraints stay outside Band messages. A separately acknowledged model request still receives the normal supplier/public-evidence model context. Packet fingerprints bind current profile, account, preferences, target variant, room configuration and reviewed roster; stale previews are rejected.

Each handoff is persisted before the single provider POST. Confirmed provider IDs are retained. Unknown submission is locked and never automatically reposted. An exact authenticated late message can establish receipt and resume an eligible still-connected run. Definitive rejection fails the run. New starts are blocked while a handoff needs investigation. The owner can explicitly abandon further processing, retaining the unknown record and without claiming provider cancellation/delivery; late messages for that run cannot trigger tools. A new run requires a fresh reviewed request.

Incoming messages must match room, exact content hash, run, expected step, sender identity and mention. Unrecognized mentions in the dedicated room are acknowledged without acting or replying. Band’s at-least-once delivery is deduplicated locally; refused claims perform no work, and a lost processing acknowledgement cannot repeat generation/charges. Refused claims and uncertain processing acknowledgements trigger up to five bounded backlog checks; exhausting them pauses the agents. These checks never repost handoffs or repeat completed model requests. Fresh roster and campaign checks precede agent work and every handoff. Participant preflight does not lock Band access atomically; verify room governance in Band.

Stopping a business leaves its room without stopping the other business’s agents. In-flight provider model work may finish or time out, but a stopped/stale result cannot apply; local refunds do not establish provider refunds. Restart disables connections and interrupts unfinished runs. A submission interrupted before its provider ID is known stays uncertain; no messages or model calls automatically replay. Campaign reset blocks active/uncertain work, stops idle project connections, and retains run/message history and usage.

## Cost, telemetry and limits

Transport and deterministic checks consume no portal credits. A completed model Builder draft consumes two local credits through the existing reservation/Flexprice gate. Actual returned input/output/total tokens are recorded per Builder and in the usage ledger, including failed responses when available. Missing usage remains unknown rather than an asserted zero. Other roles report that no model was invoked. The UI separates these portal costs from unverified Band/model provider charges; there is no fabricated dollar cost or exposed session credential.

Limits: five starts/minute/business, 200 retained runs/business, 30 room participants, four handoffs per run, 12,000-character reviewed packets, 24,000-character messages, 200 KB HTTP responses and 256 KB WS frames. The desktop shows ten recent runs; full retained history remains in SQLite. This is a single-process embedded-store prototype, not a distributed queue or production tenant isolation system.

## Validation and outstanding evidence

All 309 tests, the production build and npm audit pass locally. Thirteen provider tests cover project-only configuration, separate identities/rooms, roster consistency, exact mentions, bounded/sanitized HTTP, claim/ack semantics, header-only socket keys, channel scope, heartbeat/catch-up, reconnect and exclusive-identity conflicts. Nineteen coordination tests cover the full four-identity chain, public-packet boundaries, exact authorization, duplicate delivery and refused claims, stale/foreign packets, changed room/context, real SDK model calls under intercepted HTTP, token/cost accounting, cancellation/refund, unknown/late receipts, owner abandonment, restart, business isolation, rate/history limits and authenticated HTTP/reset.

Browser QA uses an isolated synthetic workspace. Live project credentials, real routing/reconnect behavior, Band Desktop visibility, actual provider usage/cost verification and the integration bonus remain unverified. The owner-disabled Snyk jobs still need to be re-enabled and pass actual scans.
